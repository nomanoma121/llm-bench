# llmbench Helm Chart (experimental)

This chart packages the current single-replica harness and the resources for an Agent Sandbox GPU workspace. Install the upstream Agent Sandbox controllers and CRDs first. The chart does not install them.

Set `harness.image.repository`, `harness.repositoryPVC`, `harness.dataPVC`, and `harness.apiTokenSecret` (a Secret with key `token`). The `harness.browser.*` values are unused: the controller no longer renders screenshots and publishes run HTML to a separate site repository instead (see `operatorConfig` `site:` in `../../examples/server-gitops.yaml`). For the GPU workspace, set `sandbox.devImage` to a CUDA/toolchain image with `python3`, `sandbox.sandboxdImage` to a pinned sandboxd image, and `sandbox.gpuResourceClaimTemplate` to an existing DRA ResourceClaimTemplate. `sandbox.modelPVC` and `sandbox.cachePVC` are optional in the template, but automatic model benchmarking requires a materialized model directory mounted at `/models/<model-id>`; the per-claim workspace is a dynamically provisioned PVC. The repository and data PVCs must be writable by UID/GID 1000 and usable on the harness node. GPU node selectors and tolerations are independent of harness scheduling.

If an operator target configures `gitops` or `operatorConfig.review`, set `harness.githubTokenSecret` to a separate Secret with key `token`. The token is only injected into the harness, never the Sandbox or browser sidecar. See `../../examples/server-gitops.yaml` for the operator-owned repository and YAML path fields. The chart creates read-only Roles and RoleBindings in the configured Argo CD and workload namespaces; installing/upgrading the release requires permission to create those resources there. The hook checks PR merge, the Application's synced revision, and target Deployment/Pod state. These checks still need a real-cluster end-to-end test.

Define at least one `operatorConfig.targets.<id>.sandbox` target with `namespace` equal to the Helm release namespace and a `warm_pool`. The Chart rejects local executor targets so submitted experiment commands do not run inside the credentialed harness Pod. The harness receives an explicit projected Kubernetes token; no sidecar holds credentials. Reviewed output is served from the site repository (a dedicated origin), not from the harness Pod.

Set `operatorConfig.targets.<id>.sandbox.namespace` and `.warm_pool` to route an explicit benchmark run to the Sandbox. The controller requires a full Git commit and a repository PVC containing that commit. The development image needs `sh`, `tar`, `python3`, `curl` when `runtime.start` is configured, and the runtime build tools. Do not enable local targets that execute untrusted experiment commands on the harness Pod. The Chart uses a Kubernetes Lease and per-run ConfigMap records; the data PVC retains artifacts. The Deployment deliberately fixes `replicas: 1` and `Recreate` because old-leader external effects and failover still need fencing and real-cluster tests. Pod anti-affinity is present for eventual multi-replica operation. There is no SSH path.

The remote client uses Kubernetes Pod port-forward to reach sandboxd. Keep access to `pods/portforward` and SandboxClaims tightly scoped to this ServiceAccount. The Sandbox Pod has no API token and does not expose sandboxd through a Service. Pick a workspace StorageClass that can reattach after a GPU node failure; a node-local volume cannot satisfy that requirement. The workspace is per Claim and may be deleted with it; use a separate PVC for reusable build/model caches and export artifacts before release.

Publishing to a dedicated static origin keeps generated HTML away from the harness credentials and network; enforce a CSP with a fixed script allowlist and no outbound connections on that origin (see `docs/architecture.md` §4.9). A Git archive also omits submodule contents (the controller rejects commits with gitlinks) and does not materialize Git LFS objects. If `operatorConfig.review` is enabled, provide a public HTTPS ingress for `review.public_base_url` and do not publish private artifacts. A Discord webhook Secret with key `webhook` is optional via `harness.discordWebhookSecret`.
