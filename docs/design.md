# Design

## Goal and repository contract

The current benchmark asks a model to create a 3D scene in HTML. A person judges the rendered baseline and candidate. Model comparison and runtime optimization use the same benchmark prompt; optimization is model-specific.

`benchmarks/` holds reusable tasks. `models/models.yaml` describes model sources, while downloaded files under `models/<id>/` are ignored. `runtimes/<engine>/<variant>/` holds source trees, including any CUDA code owned by the upstream runtime. `experiments/<model>/<id>/` holds one candidate's execution recipe (`config.yaml`), hypothesis and interpretation (`README.md`), and selected HTML (`output/`). A run ID denotes one actual execution; retries have distinct IDs. Run output is retained separately until the Agent chooses what to commit.

## Human workflow

1. An Issue starts an optimization session and identifies the initial baseline. An Agent opens one draft benchmark PR with runtime changes and experiment files. Each experiment's README states the intended change and expected result before execution. A benchmark-only run does not require an Agent or an Issue: a person or CI explicitly submits a fixed experiment recipe.
2. An explicit request starts a run or optimization round. The controller records the exact input commit and experiment ID. Opening or editing a PR alone does not consume the GPU.
3. A separate manifest repository is the desired state for inference workloads. The controller opens a pause PR; a human merges it. After Argo CD has applied it and the relevant inference Pods have stopped, the controller claims an Agent Sandbox backed by a Pod with a GPU ResourceClaim. The Sandbox uses an operator-approved development image, a checked-out source revision, and persistent model/build caches; it builds and executes the runtime inside the Pod. No image rebuild is needed for each source edit.
4. The harness and Agent session run outside the GPU Sandbox. They operate it remotely through the Agent Sandbox client/runtime API (or Kubernetes Pod exec where needed), and reconnect to its Claim if the backing Pod is replaced. Benchmark-only mode invokes the same runner without an Agent. An optimization round may keep the Sandbox for multiple edit/build/test attempts, but must not hold the GPU while waiting for human judgment. The controller saves artifacts outside the Sandbox, releases it, and opens a restore PR. Restoration proceeds even if execution fails. The restore PR may be auto-merged where policy permits. The controller waits for Argo CD and inference Pod readiness before requesting human judgment. Direct Kubernetes scaling is not part of this workflow.
5. The controller posts links to the baseline/candidate preview pages in the originating Issue. Permanent publication is a separate, later step: a human adopts the accepted artifact into `experiments/<model-id>/<experiment-id>/output/` and merges it, and CI publishes the merged artifacts only. The evaluator answers A, B, tie, or invalid, with optional notes. Discord may send a link to the Issue, but the Issue is the canonical evaluation history. The Agent writes the outcome and analysis in the experiment README, then may repeat within the same PR.
6. The final PR summarizes the chosen candidate, experiment IDs, human judgments, and known limits. Model comparisons may link experiments under different model directories without changing the layout.

The Agent must use an LLM independent of the inference workload being paused. Only the inference workload for the selected target is stopped. Baseline and candidate use the same prompt and the same recorded generation conditions, with one output each for the initial visual comparison. The controller executes recipes and records artifacts without an Agent; interpreting visual quality remains a human decision. Agent involvement is for proposing optimization changes and writing analysis, not a prerequisite for benchmark execution.

## Controller boundaries

- Experiment configuration specifies model, runtime, context, start command, invocation command, and benchmark reference. It does not grant authority to edit manifests, select arbitrary Pod security settings, or choose SSH hosts.
- Target IDs are allowlisted in operator-controlled configuration. Sandbox templates, ResourceClaim references, GitOps manifest paths, Argo CD Applications, and inference workloads are operator-owned. The operator config file is selected by a CLI flag; credentials are environment variables or Helm Secrets. Experiment authors cannot override privileged target settings. The GitOps adapter currently edits one unique YAML scalar path in an allowlisted file and requires explicit active/paused values; it refuses an unexpected value instead of guessing how to patch a manifest.
- Run orchestration is an ordered set of `Acquire`/`Release` hooks (command hooks, the GitOps pause/restore hook, the Agent Sandbox claim hook). Inference pause/restore and the GPU claim are injected implementations. The per-target lock is **not** a hook: the engine's `LeaseStore` acquires it write-ahead and releases it as the final step of `releasing`. The GPU ResourceClaim belongs to the Sandbox Pod and is released with that Pod; it is not a substitute for the controller's workflow lock. Releases occur in strict reverse order: an earlier resource is not restored until a later resource has been released. Releases must be idempotent. A restart and a periodic retry loop revisit unfinished releases; a run cannot be considered complete while restoration is pending.
- A hook can report acquisition as pending when external approval or convergence is still outstanding. The controller records `awaiting_acquire`, retries the same hook after a restart or on its periodic tick, and does not run later hooks or the benchmark until acquisition succeeds. Earlier acquired hooks stay held; configure ordering accordingly. Hook acquisition must be idempotent because a crash can occur after an external effect but before success is recorded. Operator command hooks reserve exit code 75 for this pending result. Release failures remain `needs_restore` and are retried in reverse order.
- The executable captures input identity (PR commit, model revision, runtime source, prompt hash), output identity, and run state. One target cannot host overlapping runs.
- Controller credentials are scoped to its integrations and are not exposed to the Sandbox or experiment configuration. GPU Sandbox Pods are non-privileged, have no Kubernetes API token, and do not receive manifest-write credentials. The Agent may direct development commands into the Sandbox through the harness, not onto the host. CUDA application kernels can be built there; host drivers, kernel modules, and node-level tuning are outside this project's execution path. There is no SSH executor.
- Agent Sandbox is an external cluster prerequisite. An operator-owned SandboxTemplate defines the CUDA development image, sandbox runtime, model/build volumes, and GPU claim. A SandboxWarmPool with zero idle replicas avoids reserving a scarce GPU before a run. The harness uses the official Go client with sandboxd via Kubernetes Pod port-forward; sandboxd is not exposed through a Service. Commands are not automatically retried after transport loss because they may have side effects. Claim names derive from run IDs, so a fresh harness can locate an existing Claim without relying on process memory. Reconnection after a Pod replacement is an explicit operation, not a claim that an interrupted build resumes.
- Multiple harness replicas would require Pod anti-affinity, leader election, durable run/session state and recovery that reattaches to an existing SandboxClaim. Leader election and durable records now exist in the controller, but external-effect fencing and failover are unproven, so multi-replica operation stays disabled. The Helm chart is currently a values-only scaffold and installs nothing.

## Initial implementation boundary

The current Go control plane provides the experiment parser, local and Sandbox command runners, injectable per-target hooks, GitHub pause/restore PR hooks, restart cleanup, HTTP API, CLI, static-site publication, and tests. A Sandbox target requires a full Git commit in the explicit request. The controller verifies that the experiment and prompt match that commit before running any hooks, archives that commit, and uploads it to the Sandbox. It runs one benchmark without an Agent and copies HTML/logs to harness storage. Mounted model files are hashed before and after execution, with an optional operator-pinned digest. The GitOps hook checks the merged manifest value, a single-source Argo CD Application's synced revision, and the target Deployment/Pods before proceeding or declaring restoration complete. Issue A/B review (the Issue is the canonical vote history), optional Discord links, Kubernetes ConfigMap run state, target leases, and leader election have been added. The Helm Chart is still a values scaffold without templates. An optimization-round engine does not exist yet: multiple attempts in a round, the Agent process and their artifact capture are unconnected. GitOps and cluster checks have fake-client and cross-component tests, not a real-cluster end-to-end verification. Multi-replica operation stays disabled until external-effect fencing and failover are proven; the Helm Chart is a values-only scaffold without templates. `docs/plan.md` tracks operational completion separately from implemented components.
